# 安全模型

DSH 能在电脑上读写文件、执行命令。**能控制 DSHRemote，就等于能控制这台电脑**，所以安全是本项目的第一优先级。

## 核心原则

**网络只负责连通，安全完全由 App 和插件自己保证。**用户可能在家里的 Wi-Fi、咖啡馆的公共 Wi-Fi 或 Tailscale 上使用，App 无法判断当前网络是否可信，所以按「网络不可信」来设计。

## 要防御的威胁

| 威胁 | 场景 | 对策 |
|---|---|---|
| 抓包窃听 | 同一 Wi-Fi 上有人抓包 | 全程 TLS |
| 中间人攻击 | 有人伪装成你的电脑 | App 只认配对时拿到的证书指纹 |
| 未经授权的连接 | 同一网络里的人直接连接插件端口 | 所有接口都要求设备 token；配对码一次性、限次数、5 分钟过期 |
| 暴力猜测配对码 | 反复尝试配对码 | 8 位配对码；输错 5 次作废并锁定 |
| 手机丢失 | 有人拿到你的手机 | 在本机配对页撤销该设备；token 保存在 Android Keystore 加密的存储里 |
| 恶意网页攻击本机配对页 | 电脑浏览器里打开了恶意网页：DNS rebinding 读取页面内容；或跨站提交表单，偷偷生成配对码、撤销设备 | 配对页只监听 `127.0.0.1`，并校验 Host 必须是回环地址；会改变状态的操作同时校验 Origin、Content-Type 和 CSRF token；禁止被嵌入框架（防点击劫持） |
| 凭据泄露 | 日志、截图、报错信息里出现 token | 不记录敏感信息；token 只在配对响应里出现一次 |
| 插件绕过 DSH 的安全机制 | 为了省事改 DSH 的内部配置 | 只使用公开接口；DSH 自己的 Host 和 Origin 校验保持不变 |

## 插件在 DSH 中的身份

插件以 **owner** 身份访问 DSH（ADR 0008），因为只有 owner 能处理审批和提问（见[调研文档](research/dsh-session-api.md) 5.4）。这意味着：

- 设备 token 一旦泄露，攻击者就拥有和你本人一样的 DSH 权限。所以 token 的保管、撤销以及配对码的防护都是重中之重。
- 外观层只开放 `protocol.md` 中列出的操作，**不提供通用的 DSH 调用通道**。这样即使 token 泄露，攻击者也只能做 App 能做的事，不能修改设置或安装插件。
- 以后改用非 owner 的受限身份，由 DSH 自己的权限系统再提供一层保护，见 roadmap 第 2 条。
- 切换权限模式在 DSH 中是一条 `/permission <模式>` 命令。插件只会拼出这一条命令，模式名必须在 DSH 给出的列表中，**不提供执行任意命令的能力**（有反向测试）。
- 插件一直连着 DSH 的事件流，所以 DSH 认为「始终有人能回答审批」。没有任何窗口和手机在线时，需要审批的操作会**一直等待**，而不是像没装插件时那样直接失败。等待不会让操作自动执行；如果不希望 Agent 在无人看管时卡住，请使用更严格的权限模式，或在不用时停用插件。

## App 端的证书校验

插件的证书是自签名的，电脑的地址也会变化（局域网 IP、Tailscale 地址等），所以 HTTPS 默认的两道检查都要由 App 自己实现：

| 默认的检查 | 默认做法 | App 的做法 |
|---|---|---|
| 证书是否可信（TrustManager） | 对照系统内置的根证书 | 比对证书公钥的 SPKI SHA-256 指纹和配对时保存的指纹，不一致就拒绝握手 |
| 证书是否属于要连接的地址（HostnameVerifier） | 比对证书上的域名或 IP | **再比对一次指纹**（取握手得到的证书），不一致就拒绝 |

- 两道检查都只认指纹。任何一道写错，另一道仍然能拦住中间人。HostnameVerifier 以指纹比对代替主机名比对，**不属于**红线第 1 条禁止的「信任所有的 HostnameVerifier」；写成无条件放行（例如 `{ _, _ -> true }`）才违反红线。
- 两道检查写在同一个文件里（`android/` 的 `data/net/`），所有请求都只能通过它创建的客户端发出。
- **地址不是信任的依据，指纹才是。**所以 App 允许用户修改和添加电脑的地址：连到错误的地址时，指纹校验失败，握手中止，token 根本不会发出。
- **手动输入地址配对时**，App 需要先取得服务器的证书，才能显示指纹让用户核对。为此使用一个专门的「探测」TrustManager：它只记录收到的证书，然后**一定中止握手**，这条连接不会发送任何应用数据。用户核对指纹一致后，App 才保存这个指纹，再用正常的指纹校验连接、发送配对码。探测逻辑同样需要反向测试，并列入人工审查。

## 不在防御范围内

- 电脑本身已经被入侵（这时攻击者已经可以直接控制 DSH）。
- 用户主动把配对二维码或 token 发给别人。
- 手机已经被 root 并且被植入了恶意软件。

## 红线

见 `AGENTS.md` 的「安全红线」一节。任何代码审查都必须对照那几条检查。

## 安全相关代码的审查要求

以下几类改动合并之前，必须由人工逐行检查 diff，并确认有反向测试用例：

- App 端的证书校验（TrustManager）和 OkHttp 的配置
- 插件端的 TLS 配置、证书生成、指纹计算
- 配对码的生成、校验和锁定逻辑
- token 的生成、存储和校验
- 转发给 DSH 时对请求头的处理
- 本机配对页的访问控制
