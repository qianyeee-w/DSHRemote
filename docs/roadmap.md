# 后续优化方向

这里记录已经讨论过、但**不在 v1 范围内**的方向。v1 不实现这些功能，但其中标注了「v1 需预留」的设计约束，v1 写代码时必须遵守，这样以后接入时不需要大改结构。

---

## 1. DSH 新版本自动兼容检测 + agent 适配

- 状态：第 1、2 步已实现（M3 T1，`.github/workflows/dsh-compat.yml`，设计见 `docs/plans/m3-release.md` T1）；第 3 步以后仍由人手动发起
- 背景：DSH 还在开发者预览阶段，发版很频繁（0.2.1-rc.1 到 0.2.2-rc.1 只用了三周左右），不兼容的改动随时可能出现。用户的官方 Desktop 可能会自动升级，一旦超出插件支持的范围，插件就会失效。

### 目标

DSH 一出新版本就能自动发现兼容问题，并由 agent 完成大部分适配工作，人只需要审查改动。

### 设想的流程

1. **定时检测**：CI 中加一个定时任务（例如每天一次），安装 `@deepseek-ai/dsh` 的最新版本，包括 latest 和预发布版本，对它运行插件的接口契约测试。
2. **自动报告**：测试失败时，自动开一个 issue。内容包括：新版本号、失败的测试和接口、对应版本的官方升级指南链接（`docs/upgrade-guide/<版本号>/`）。同一个版本只开一个 issue。
3. **agent 适配**：agent 接手这个 issue，阅读升级指南，只修改插件的 DSH 适配层，跑通契约测试和全部测试后提交 PR。
4. **人工审查**：人审查 PR，确认后合并。
5. **升级基线**：新写一条 ADR，更新 `AGENTS.md` 中的 DSH 基线版本，以及插件的 `engines.dsh` 范围。

### v1 需预留的设计

以下约束 v1 必须遵守：

| 约束 | 原因 |
|---|---|
| **所有对 DSH 的调用都集中在插件的适配层**（`plugin/src/dsh/`），其他模块不允许直接调用 DSH 的接口 | DSH 改接口时，只需要改这一处；agent 适配时修改范围清楚 |
| **App 不直接依赖 DSH 的数据格式**，只依赖 `docs/protocol.md` 定义的接口 | DSH 升级时 App 不需要重新发布。如果 v1 选择了透传方案，透传的范围也要在 protocol.md 中明确列出 |
| **契约测试独立成一组**（`plugin/test/contract/`），用环境变量 `DSH_VERSION` 指定要测试的 DSH 版本，未指定时使用基线版本 | 定时任务直接复用这组测试，只需要换一个版本号 |
| **契约测试输出机器可读的结果**（例如 JSON：每个接口是否通过、失败原因） | 方便自动生成 issue，也方便 agent 读取 |
| **支持的 DSH 版本范围只在一个地方定义**，`engines.dsh` 和运行时的版本检查都从这里读取 | 升级基线时只改一处 |
| **启动时检测 DSH 版本**，不在支持范围内时，通过 `/v1/info` 和配对页明确提示「DSH 版本不兼容」，不要带病运行 | 用户的 Desktop 自动升级后，能看到明确的原因，而不是莫名其妙的错误 |

### 以后再决定的问题

- ~~检测哪些版本~~：已确定（M3 T1）。检测 npm 上 latest、next、alpha 三个渠道中比基线新的版本，每天一次，只在 Linux 上跑（手动触发可以选 Windows）。
- agent 怎么被触发：手动指派 issue，还是由 CI 自动调用 agent。
- 是否要同时支持多个 DSH 版本（例如适配层按版本分支）。目前的倾向是不支持，只跟随一个基线版本。

## 2. 手机以非 owner 的受限身份接入 DSH

- 状态：计划中，后续做（v1 只用 owner 身份，见 [ADR 0008](decisions/0008-owner-principal-for-v1.md)）
- 前置条件：DSH 允许非 owner 的身份（principal）回答审批和提问这类 waterfall 事件。目前不允许（见[调研文档](research/dsh-session-api.md) 5.4），这一项依赖官方的进展。

### 背景

DSH 区分两层概念：principal 表示「调用方是谁、有什么权限」，peer 表示「是哪一条连接」。owner 是本机用户，不受任何权限检查。非 owner 的身份（目前只有 liveshare 的分享读者）由 `remote-access` 包按角色限制权限。

v1 的插件以 owner 身份访问 DSH，只在外观层限制手机能做的操作（安全红线第 8 条）。设备 token 一旦泄露，攻击者能做的就是 App 能做的全部操作。

### 目标

为每部配对的手机在 DSH 中建立一个**非 owner 的受限身份**，只授权 v1 需要的操作：查看会话、发消息、停止任务、处理审批和提问、切换模型和权限模式。不授权修改设置、管理插件、读写凭据等操作。这样在插件的外观层之外，DSH 自己的权限系统再提供一层保护：即使插件有漏洞，手机也越不过 DSH 的权限检查。

### 要做的事（届时细化）

1. 确认 DSH 已经允许非 owner 身份回答 waterfall 事件，并阅读对应版本的升级指南和 `remote-access` 文档。
2. 在插件中为手机定义 principal 类型和 role（可执行的操作集合），并注册访问策略（`registerPolicy`）。
3. 插件以该手机对应的身份调用 DSH，而不是以 owner 身份调用。
4. 撤销设备时，同时让 DSH 中对应的身份失效（`invalidate`）。
5. 新写一条 ADR，取代 ADR 0008。

### v1 需预留的设计

| 约束 | 原因 |
|---|---|
| 插件内部用独立的设备身份（`deviceId`）标识请求来自哪部手机，不和 DSH 的 owner 身份混用 | 以后要把 `deviceId` 映射成 DSH 中的受限身份 |
| 适配层（`plugin/src/dsh/`）中所有对 DSH 的调用，都通过一个统一的入口发出，并且这个入口能拿到当前请求对应的 `deviceId` | 以后切换身份时，只需要改这一个入口 |
| 外观层的每个操作都能映射到一个明确的 DSH 接口（`protocol.md` 中逐项列出） | 以后为受限身份定义 role 时，可以直接按这张表授权 |

## 待评估：`ask_user_question` 的限时模式

DSH 的 `ask_user_question` 可以配置为限时模式（`mode: "timed"`）：没有界面认领时，超时后提问转为「之后还能回答」的状态，并从手机端撤回。v1 只支持默认的阻塞模式。要支持限时模式，插件需要认领等待（`userQuestions/attachWait`）并用 `userQuestions/answer` 回答已经转为 continued 的提问。见调研文档 5.8。
