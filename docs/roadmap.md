## 开发优先级（2026-11-12 建议稿，待用户确认）

> 这是 agent 整理的建议，**用户确认前不按它开工**。确认后把标题改为「已确认」并写上日期。每完成一个阶段，或者范围有变化时，同步更新这一节。

把下面几处记录的待办合在一起排序：本文第 1–3 节和文末的待评估项、`spec-v1.md` 的「第二版」和「以后再说」、M3 计划，以及 M2 和视觉改版留下的已知问题。

**排序原则**

1. **先让 v1 稳定可用。** 用户每天都在用的功能出了问题，影响比缺新功能大。
2. **先做被依赖的基础。** 通知操作按钮和云推送要靠准确的事项状态和「补看遗漏结果」才能做对，所以排在它们后面。
3. **先只读，后可写，风险由低到高。** 文件写入、Git 操作、终端会扩大手机能做的事，每项都要先写 ADR、更新安全模型。
4. **依赖外部进展的不排期。** 例如等 DSH 放开权限的，放到「被动处理」。

## 1. DSH 新版本自动兼容检测 + agent 适配

- 状态：第 1、2 步已实现（M3 T1，`.github/workflows/dsh-compat.yml`，设计见 `docs/plans/m3-release.md` T1）；第 3 步以后仍由人手动发起
- 背景：DSH 还在开发者预览阶段，发版很频繁（0.2.1-rc.1 到 0.2.2-rc.1 只用了三周左右），不兼容的改动随时可能出现。用户的官方 Desktop 可能会自动升级，一旦超出插件支持的范围，插件就会失效。

### 目标

DSH 一出新版本就能自动发现兼容问题，并由 agent 完成大部分适配工作，人只需要审查改动。

### 设想的流程

1. **定时检测**：CI 中加一个定时任务（例如每天一次），安装 `@deepseek-ai/dsh` 的最新版本，包括 latest 和预发布版本，对它运行插件的接口契约测试。
2. **自动报告**：测试失败时，自动开一个 issue。内容包括：新版本号、失败的测试和接口、对应版本的官方升级指南链接（`docs/upgrade-guide/<版本号>/`）。同一个版本只开一个 issue。
3. **agent 适配**：agent 接手这个 issue，阅读升级指南，只修改插件的 DSH 适配层，跑通契约测试和全部测试后提交 PR。
4. **人工审查**：人审查 PR，确认后合并。
5. **升级基线**：新写一条 ADR，更新 `AGENTS.md` 中的 DSH 基线版本，以及插件的 `engines.dsh` 范围。

### v1 需预留的设计

以下约束 v1 必须遵守：

| 约束 | 原因 |
|---|---|
| **所有对 DSH 的调用都集中在插件的适配层**（`plugin/src/dsh/`），其他模块不允许直接调用 DSH 的接口 | DSH 改接口时，只需要改这一处；agent 适配时修改范围清楚 |
| **App 不直接依赖 DSH 的数据格式**，只依赖 `docs/protocol.md` 定义的接口 | DSH 升级时 App 不需要重新发布。如果 v1 选择了透传方案，透传的范围也要在 protocol.md 中明确列出 |
| **契约测试独立成一组**（`plugin/test/contract/`），用环境变量 `DSH_VERSION` 指定要测试的 DSH 版本，未指定时使用基线版本 | 定时任务直接复用这组测试，只需要换一个版本号 |
| **契约测试输出机器可读的结果**（例如 JSON：每个接口是否通过、失败原因） | 方便自动生成 issue，也方便 agent 读取 |
| **支持的 DSH 版本范围只在一个地方定义**，`engines.dsh` 和运行时的版本检查都从这里读取 | 升级基线时只改一处 |
| **启动时检测 DSH 版本**，不在支持范围内时，通过 `/v1/info` 和配对页明确提示「DSH 版本不兼容」，不要带病运行 | 用户的 Desktop 自动升级后，能看到明确的原因，而不是莫名其妙的错误 |

### 以后再决定的问题

- ~~检测哪些版本~~：已确定（M3 T1）。检测 npm 上 latest、next、alpha 三个渠道中比基线新的版本，每天一次，只在 Linux 上跑（手动触发可以选 Windows）。
- agent 怎么被触发：手动指派 issue，还是由 CI 自动调用 agent。
- 是否要同时支持多个 DSH 版本（例如适配层按版本分支）。目前的倾向是不支持，只跟随一个基线版本。

## 2. 手机以非 owner 的受限身份接入 DSH

- 状态：计划中，后续做（v1 只用 owner 身份，见 [ADR 0008](decisions/0008-owner-principal-for-v1.md)）
- 前置条件：DSH 允许非 owner 的身份（principal）回答审批和提问这类 waterfall 事件。目前不允许（见[调研文档](research/dsh-session-api.md) 5.4），这一项依赖官方的进展。

### 背景

DSH 区分两层概念：principal 表示「调用方是谁、有什么权限」，peer 表示「是哪一条连接」。owner 是本机用户，不受任何权限检查。非 owner 的身份（目前只有 liveshare 的分享读者）由 `remote-access` 包按角色限制权限。

v1 的插件以 owner 身份访问 DSH，只在外观层限制手机能做的操作（安全红线第 8 条）。设备 token 一旦泄露，攻击者能做的就是 App 能做的全部操作。

### 目标

为每部配对的手机在 DSH 中建立一个**非 owner 的受限身份**，只授权 v1 需要的操作：查看会话、发消息、停止任务、处理审批和提问、切换模型和权限模式。不授权修改设置、管理插件、读写凭据等操作。这样在插件的外观层之外，DSH 自己的权限系统再提供一层保护：即使插件有漏洞，手机也越不过 DSH 的权限检查。

### 要做的事（届时细化）

1. 确认 DSH 已经允许非 owner 身份回答 waterfall 事件，并阅读对应版本的升级指南和 `remote-access` 文档。
2. 在插件中为手机定义 principal 类型和 role（可执行的操作集合），并注册访问策略（`registerPolicy`）。
3. 插件以该手机对应的身份调用 DSH，而不是以 owner 身份调用。
4. 撤销设备时，同时让 DSH 中对应的身份失效（`invalidate`）。
5. 新写一条 ADR，取代 ADR 0008。

### v1 需预留的设计

| 约束 | 原因 |
|---|---|
| 插件内部用独立的设备身份（`deviceId`）标识请求来自哪部手机，不和 DSH 的 owner 身份混用 | 以后要把 `deviceId` 映射成 DSH 中的受限身份 |
| 适配层（`plugin/src/dsh/`）中所有对 DSH 的调用，都通过一个统一的入口发出，并且这个入口能拿到当前请求对应的 `deviceId` | 以后切换身份时，只需要改这一个入口 |
| 外观层的每个操作都能映射到一个明确的 DSH 接口（`protocol.md` 中逐项列出） | 以后为受限身份定义 role 时，可以直接按这张表授权 |

## 3. 后续阶段的功能范围（2026-11-10 确认）

用户既会在手机上跟进已有任务，也会直接发起编码任务。本节记录后续设计范围。用户随后确认优先实现创建／导入项目（见 `plans/project-create-import.md`），M3 剩余任务顺延；其他功能的具体版本和排期尚未确定。

`spec-v1.md` 中「第二版」和「以后再说」是最初的方向分类；其中功能的最新取舍以本节为准。未在本次确认的其他方向不自动纳入下一阶段。

### 纳入后续设计的功能

| 功能 | 最小设计范围与约束 |
|---|---|
| 准确的执行结果 | 区分本轮结束、失败、已停止、等待处理；无法确认时显示结果待确认。运行结束不能直接等同于需求完成或测试通过，通知措辞应与真实状态一致 |
| 待处理与未读结果 | 保留现有待处理事项同步，增加未读结果、近期失败和已读状态；断线后能补看遗漏结果，避免大量补发过期通知。进程重启后通知入口应能安全恢复并重新校验事项状态 |
| 只读改动查看 | 改动文件列表、增删行数、Diff 和必要上下文；明确比较基线与范围，不把工作区内其他人的修改标成当前任务的修改 |
| 草稿与可靠发送 | 按会话保存草稿和未确认的发送记录，区分未发送、已受理、排队、失败和结果不确定；回执丢失时不能盲目自动重发 |
| 会话快速定位 | 标题和工作区／目录搜索，按状态及未读结果筛选；聊天和审批页面清楚显示电脑、工作区和当前权限模式 |
| 创建／导入项目 | **已实现**（2026-11-11，ADR 0013，`plans/project-create-import.md`）：选择电脑上的父目录创建项目，或将已有目录注册为 DSH 工作区，再开始会话 |
| 计划／目标仪表盘 | 当前目标、计划步骤、当前步骤、阻塞原因和最近进展，以 DSH 的真实状态为依据；展示目标与让 Agent 持续追求目标分别评估，不猜测完成百分比 |
| 远程终端 | 工作目录、交互输入输出、停止和断线恢复；默认关闭，单独控制启用。能力来源及授权边界需先设计 |
| 完整文件管理 | 按浏览预览、上传下载、创建修改删除分批设计，明确工作区范围 |
| 通知操作按钮 | 提供「允许本次／拒绝」，必须解锁后才能提交审批；详见下节 |
| 云推送 | 审批、提问和任务结果提醒；仅承担通知投递，不承载会话和控制请求。通道与部署方案待调研，不预先指定 FCM |

### 通知操作按钮：锁屏限制是硬性要求

- **手机锁屏时不能执行允许或拒绝，不能向插件发送审批请求。** 不能只依靠隐藏按钮实现这个限制，操作入口本身也必须校验。
- 锁屏状态下点击通知操作后必须先解锁；用户取消解锁时，不提交任何审批。
- 解锁后提交前重新确认事项仍待处理，电脑已处理、任务已停止、设备已撤销时不得重复执行。提交时发生并发处理，仍遵守协议的 `ATTENTION_RESOLVED` 语义。
- 无法连接电脑或无法确认当前状态时，不显示审批成功，也不把审批保存为待联网后自动执行的操作。
- 锁屏通知继续隐藏命令、参数和问题内容；操作入口继续满足 `security.md` 中防伪造的要求。

实现时必须包含反向测试和真机验收：锁屏点击不发请求、取消解锁不发请求、事项在解锁期间被电脑处理后不再生效、重复点击不会重复处理、伪造操作入口被拒绝。验证范围覆盖最低支持的 Android 版本对应的处理路径及现有小米真机。

### 云推送的边界

- 云推送已纳入后续设计，具体服务商、是否需要配套服务、凭据管理、成本和部署方式尚未确定。优先验证现有小米真机的接收效果，不能只以模拟器或其他品牌手机的结果判断可用。
- 会话内容和控制操作仍通过现有 HTTPS/WSS 通道，继续校验证书指纹与设备 token；用户仍需局域网或自行配置的 Tailscale／VPN。**收到推送不代表手机已经能连接电脑。**
- 云推送不替代插件的认证和审批接口，也不绕过通知按钮的解锁要求。推送正文与标识的隐私处理需在方案中明确，不在通知载荷中携带设备 token、配对码、私钥或 DSH cookie。
- 与实时连接收到的通知去重；处理延迟到达、重复到达和事项已经失效的情况，最终以插件当前状态为准。
- 不承诺在所有系统限制、强制停止或无网络情况下实时送达；保留断线后的未读结果补看能力。

### 备选与暂不纳入的功能

| 状态 | 功能 |
|---|---|
| 备选 | 图片附件。先确认 DSH 所选模型和公开接口支持理解图片，仅支持上传不等于支持看图分析 |
| 不纳入本阶段 | 语音输入 |
| 暂不考虑 | 中转服务、自动穿透；云推送的引入不意味着同时建设会话或控制流量的中转 |
| 不做（2026-11-11 决定） | Git 提交与回滚。提交、撤销等操作直接在对话里交给 Agent 完成，相关命令仍按当前权限模式经过审批；手机上不单独提供 Git 界面 |
| 正在评估 | 用户要求分析桌面端的 token 用量、缓存命中、对话分支、思考／整轮过程折叠；截图中的会话性能和上下文占用一并核实。源码与样本结论见下节，尚未确认具体排期 |

### 桌面能力的可行性（2026-11-10 调研）

详见 [`DSH 接口调研`](research/dsh-session-api.md) 第 9 节。以下结论来自固定基线 `dsh-v0.2.2-rc.1` 的官方源码与仓库已录制样本，不代表新接口已运行验证或功能已实现。

- token 用量和缓存命中：公开会话统计数据已存在；本轮精确用量还需完整的轮次／尝试边界，避免重试和流式最终值重复计数。
- 会话性能和上下文占用：有公开统计数据；缺少对应组件或字段时显示不可用。上下文构成是估算值，不能当作精确计费。
- 新对话分支：有公开 `session/fork` 接口；需要在外观协议中补充可靠的分支位置与轮次边界。它分出对话历史，不创建 Git 分支，也不回滚工作区文件。
- 单块思考折叠：Android 已实现默认折叠。截图中的整轮「已完成／用时」折叠栏还需要轮次分组、状态与耗时，不能仅增加一个按钮。

### 建议顺序与实施前提

1. 先补执行结果、遗漏结果恢复、消息可靠性和会话定位。
2. 尽早调研 DSH 的公开接口，设计创建／导入项目、Diff、计划／目标和文件查看；创建／导入项目优先于完整文件管理与远程终端，Diff 的比较范围必须先确定。
3. 基于上述状态和恢复能力设计通知按钮与云推送，先验证锁屏限制和真机投递。
4. 再分任务实现文件写入和终端；图片保持备选。

以上是依赖关系建议，不是已确认的任务排期（排序建议见本文开头的「开发优先级」）。涉及 DSH 新能力时先用真实 DSH 验证公开接口；涉及协议变化先修改 `protocol.md`；涉及推送信任边界、终端或文件写入等架构变化时先记录 ADR 并同步安全模型，再修改实现。不得通过通用 DSH 调用通道或私有字段绕过现有安全红线。

## 待评估：`ask_user_question` 的限时模式

DSH 的 `ask_user_question` 可以配置为限时模式（`mode: "timed"`）：没有界面认领时，超时后提问转为「之后还能回答」的状态，并从手机端撤回。v1 只支持默认的阻塞模式。要支持限时模式，插件需要认领等待（`userQuestions/attachWait`）并用 `userQuestions/answer` 回答已经转为 continued 的提问。见调研文档 5.8。
