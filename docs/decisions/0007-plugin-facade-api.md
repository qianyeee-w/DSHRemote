# 0007 插件对 App 提供外观层接口，不透传 DSH 协议

- 状态：已接受
- 日期：2026-11-08
- 依据：[DSH 0.2.2-rc.1 会话接口调研](../research/dsh-session-api.md)

## 背景

protocol.md 草案中留下了一个待定问题：App 是直接使用 DSH 的会话协议（透传），还是由插件提供一组为手机精简过的接口（外观层）。草案的初步倾向是透传。

## 决策

**采用外观层。**App 只依赖 `docs/protocol.md` 定义的 `/v1/*` 接口，不直接接触 DSH 的协议和数据格式。

插件内部通过 DSH 官方的 Remote API（HTTP 加 `/api/remote.mux`，以 owner 身份）访问 DSH，并负责：

- 把 DSH 的原始会话事件转换成精简的聊天消息
- 把审批和提问（waterfall 事件）转给 App，并把 App 的回答交还给 DSH
- 汇总会话状态，生成通知事件

所有对 DSH 的访问和转换逻辑都集中在 `plugin/src/dsh/`。

## 理由

- `session/follow` 返回的是原始内部事件（包括遥测事件），格式还在演进（会话头 `version: 4`）。透传的话，App 必须自己实现事件转换，并直接依赖这些格式。
- DSH 一元调用的 `args` 字段名就是 Host 方法的参数名，官方改一个参数名就会改变 wire 格式。
- DSH 发版很频繁（三周内发布了 5 个以上 rc 版本）。用外观层的话，DSH 升级时只需要修改并发布插件，App 不受影响。
- 符合 roadmap 中「DSH 新版本自动适配」的预留设计。
- 手机只收到需要的数据，可以节省流量和电量。

## 代价 / 后果

- 插件的工作量变大，事件转换器是 M1 的主要工作。
- DSH 新增的功能不会自动出现在 App 里，需要在外观层中手动接入。
- 插件必须正确实现多客户端场景：同一个审批请求可能同时出现在手机和 Desktop 窗口上，任一端处理后，要通知另一端收起这个请求。
- 推翻了 protocol.md 草案中「倾向透传」的初步判断，protocol.md 已同步修改。
